## Affected pages / routes

| Path | What to test and why |
|---|---|
| `/dashboard/reports` | Report list now comes from `generated_reports` via the server page, not from client state. Every row must survive a hard reload. |
| `/dashboard/history` | The unscoped browser query is removed. Report actions must still work, now through server routes. |
| `POST /api/reports/generate` | Orchestrator. Type validation, provenance classification, abort, finalize check. |
| `GET /api/reports/[id]/preview` | New. Owner-scoped, issues a fresh link every call. |
| `GET /api/reports/[id]/download` | Now owner-only; accepts `degraded`. |
| `POST /api/v1/reports/generate` | Report service. Ownership-scoped, fails closed without `BACKEND_API_KEY`. |

## Key interactions to verify

- Generate a report of **each of the four types** from the reports page. All four render.
- Generate from the **history** page. It must no longer hard-code `patient_report`.
- Open **preview** on a report generated over an hour ago. The link must work — it is re-signed on demand, not reused.
- **Download** a report. The filename must be `{report_number}.pdf` and must match the number printed inside the PDF and shown in the list.
- Generate the **same analysis and type twice**. Two rows, two distinct report numbers, two stored documents. The first must remain openable and unchanged.
- Reload the page mid-generation. The in-flight report must still be there.
- Sign in as a **second account** and attempt to open the first account's report id via preview and download. Both must refuse identically and reveal nothing.

## Edge cases

| Case | Expected user-visible outcome |
|---|---|
| Report service unreachable | "Report generation service is unavailable." Row marked failed. No document stored. |
| Report service accepts but never responds | After 240s: report shows *Couldn't be generated*. Never an endless spinner. |
| Orchestrator process dies mid-generation | Row shows *Didn't finish* once older than 300s. Regenerating works. |
| Narrative returns prose but not JSON | Report shows *Incomplete* and **names the missing sections on screen**, without opening the PDF. |
| Narrative returns empty or a refusal | *Couldn't be generated*. No PDF stored. Never a report with no narrative. |
| Provenance headers absent from the response | Report shows *Incomplete*, reason "provenance unavailable". Never *Ready*. |
| Analysis has no overlay | Report is produced and states the overlay was unavailable. No broken-image gap. |
| Unsupported report type posted directly | 422 naming the four valid types. Never silently substituted. |
| Config with an unknown key posted directly | 422. The unknown key is not persisted. |
| `BACKEND_API_KEY` unset on the backend | 503 with a clear log line, not a 401 and not a successful render. |
| Historical report (pre-migration) | Opens using its stored values. Completeness shows as unavailable, never as complete. |
| Storage object deleted behind a completed row | Clear "document no longer available", not a generic 500. |

## Critical paths

1. **Generate → complete → preview → download**, verified against the same report number in all four places (row, PDF body, filename, response).
2. **Generate → degraded → the interface names the missing sections** before the person opens the document. This is SC-012 and cannot be verified from the PDF alone.
3. **Cross-account access refusal** on preview and download.
4. **Reload survives** — every produced report is retrievable after a browser restart.
5. **Fresh-clone provisioning**: apply tracked migrations, then confirm
   `select generate_report_number() ~ '^MIDAS-REP-[0-9]{8}-[A-Z0-9]{6}$';` returns true.

## Confidence display check (Issue 1)

On a **clinician report**, the confidence in the header and the confidence in the metrics
panel must be the same number. Historically these came from two different fields with two
different normalizations; a row where they disagree renders e.g. `87.3%` and `8730.0%`.

## Accessibility and responsive acceptance checks

Added by `/plan-design-review` 2026-08-06. Run manually before ship. Roughly ten minutes.

**Keyboard — no mouse, starting from page load**

- [ ] Tab reaches `Generate report` on every analysis row
- [ ] Enter opens the dialog and focus lands inside it
- [ ] Tab cycles within the dialog and never reaches the page behind it
- [ ] Esc closes the dialog and focus returns to the button that opened it
- [ ] Tab reaches Preview and Download on every report row
- [ ] Every focused control shows a visible ring (`--ring` is `--primary`, 16.1:1)

**Screen reader — VoiceOver + Safari**

- [ ] Each status chip announces its word ("Incomplete"), never its colour
- [ ] The chip icon is not announced (`aria-hidden`)
- [ ] Report completion announces once via `role="status"`
- [ ] The elapsed timer on a generating row does **not** announce repeatedly

**Viewport**

- [ ] 375px: report rows are stacked cards, no horizontal scroll
- [ ] 375px: status appears first in each card, before the report number
- [ ] 375px: Preview and Download are at least 44px tall
- [ ] 768px: the table degrades without truncating the report number

**Colour and motion**

- [ ] Greyscale screenshot: Ready and Incomplete remain distinguishable
- [ ] `--warning` on `--warning-subtle` measures at least 4.5:1
- [ ] `prefers-reduced-motion: reduce` stops the `Loader2` spin

**Copy accuracy**

- [ ] No dialog description mentions "detected features"
- [ ] All four report types appear in the picker
- [ ] A degraded report's card names the missing sections without opening the PDF (SC-012)
- [ ] The PDF's provenance block is on page 1, above any clinical finding

## Not covered by automated tests

State plainly when reporting results — these need a human or the live smoke script:

- The six thin guards in `generate/route.ts` (401, no-supabase, 404, 403, insert-fail, upload-fail).
- Genuine WeasyPrint output vs a substitute (`pdfinfo | grep -qi weasyprint`).
- Anything requiring live Supabase credentials or `NVIDIA_API_KEY`.
